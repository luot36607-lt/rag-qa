# RAG 文档问答

一个最小可用的检索增强问答系统：读 `docs/` 里的文档，回答关于它们的问题，并给出引用来源。

不依赖 LangChain、向量数据库或任何框架——除了调 API，其余都是标准库。目的不是"能上线"，
而是每一层都能看懂、能替换、能量化对比。

仓库自带一份示例语料（`docs/sample.md`，一份校园事务指南），克隆下来就能跑。

---

## 快速开始

```powershell
# 1. 建虚拟环境并装依赖
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt

# 2. 配置密钥（复制模板后填值）
copy .env.example .env

# 3. 起服务
.venv\Scripts\python.exe -m uvicorn rag_api:app --reload --port 8001
```

打开 http://127.0.0.1:8001/ 是网页界面，http://127.0.0.1:8001/docs 是接口文档。

> 生成用 DeepSeek，检索用硅基流动的 `bge-m3`（免费）。两个 key 都在 `.env` 里配。

---

## 换成自己的语料

把 `.md` / `.txt` / `.py` 丢进 `docs/`（会自动递归读取），重启服务即可。
新增内容只会补算向量，已算过的走 `embed_cache.json` 缓存。

换完语料后，记得重写 `eval_set.json` 并重跑评测——否则你手里的基线就失效了。

---

## 数据流

```
docs/*.txt|md|py
      │
      ▼
 [切块] 按标题/空行分段，超长再按字数切，块间留重叠
      │
      ▼
 [检索] 向量相似度（BAAI/bge-m3）── 或 ── BM25 关键词
      │
      ▼
 [生成] 把 top-3 拼进 prompt → DeepSeek 回答并标注 [1][2]
      │
      ▼
 [返回] answer + sources（文件名 / 相似度 / 原文片段）
```

## 文件职责

| 文件 | 作用 | 备注 |
|---|---|---|
| `rag_step1.py` | 读文件、切块、BM25 打分 | 纯标准库，零依赖 |
| `rag_step2.py` | 拼 prompt、调 DeepSeek、引用约束 | `--dry` 只打印 prompt 不花钱 |
| `rag_step3.py` | 向量检索、混合检索 | 调硅基流动的 embedding |
| `rag_eval.py` | 评测：检索指标 + 生成打分 | 支持 `--vector` / `--hybrid` / `--k` |
| `rag_api.py` | FastAPI 服务 | 启动时建一次索引 |
| `web/index.html` | 网页界面 | 纯静态，无构建步骤，改文案直接改这个文件 |
| `eval_set.json` | 6 道示例评测题 + 参考答案 | 换成自己的语料后重写这里 |
| `docs/sample.md` | 示例语料 | 换成自己的资料 |
| `embed_cache.json` | 向量缓存 | 可随时删，会自动重算 |

## 常用命令

```powershell
# 交互式提问（只检索，不调模型）
.venv\Scripts\python.exe rag_step1.py docs

# 看语料到底读进来了什么（检索不出结果时先跑这个）
.venv\Scripts\python.exe rag_step1.py docs --stats

# 看模型会收到什么 prompt（不花钱）
.venv\Scripts\python.exe rag_step2.py docs --dry

# 只测检索（免费，秒出）
.venv\Scripts\python.exe rag_eval.py docs --no-llm
.venv\Scripts\python.exe rag_eval.py docs --no-llm --vector
.venv\Scripts\python.exe rag_eval.py docs --no-llm --hybrid

# 完整评测（检索 + 生成 + 打分，会产生少量 API 费用）
.venv\Scripts\python.exe rag_eval.py docs --vector
.venv\Scripts\python.exe rag_eval.py docs --vector --k 5
```

## 评测怎么做

`eval_set.json` 每条的三个字段：

```json
{
  "question": "请假超过一天找谁审批？",
  "gold": "学院审批",            // 检索是否命中（null = 不考检索，专考拒答）
  "answer": "1 天以内由辅导员审批，超过 1 天需要学院审批。"  // 用于判断回答是否正确
}
```

- **检索指标**：top-1、top-k 命中率、MRR
- **生成指标**：0 错 / 1 部分对 / 2 对，取平均
- **拒答题**：`gold` 为 `null`，考它会不会老实说"资料里没有提到"

**纪律：实验进行中不要改评测集。** 改了尺子，前后分数就没法比。

## 实验记录

> 以下数据在本地语料（15 块，约 3.6 KB）上测得，语料未随仓库发布。
> 仓库自带的示例语料可以用同样的命令复现整套流程，但具体数字会不同。

| 配置 | top-1 | top-3 | MRR | 生成 |
|---|---|---|---|---|
| BM25 · k=3 | 7/9 | 8/9 | 0.83 | 17/20（1.70） |
| **向量 · k=3** | 5/9 | **9/9** | 0.78 | **18/20（1.80）** ← 采用 |
| 向量 · k=5 | 5/9 | 9/9 | 0.78 | 15/20（1.50） |
| 混合 RRF · k=3 | 6/9 | 8/9 | 0.78 | 未测 |

**采用向量 + top-3 的理由**：模型看到的是 top-3 而不是 top-1，top-3 从 8/9 提到 9/9 才是真正
影响回答的指标；top-1 下降没有传导到最终分数。

### 切块对照

| 切块 / 重叠 | 块数 | BM25 top-1/top-3 | 向量 top-1/top-3 |
|---|---|---|---|
| **350 / 80** | 15 | **7/9 · 8/9** | 5/9 · **9/9** |
| 250 / 50 | 20 | 7/9 · 7/9 | 3/9 · 8/9 |
| 180 / 80 | 38 | 6/9 · 7/9 | 5/9 · 8/9 |
| 180 / 40 | 28 | 6/9 · 7/9 | 4/9 · 7/9 |
| 120 / 30 | 42 | 5/9 · 6/9 | 4/9 · 9/9 |

**切得更细不等于更好。** 已验证：每一档下正确答案都完整存在于某个块里，没有被切碎；
变差是因为每块携带的上下文变少，加上高重叠率制造了大量近似重复块。

## 踩过的坑

**1. 语料污染**
把评测题文件放进语料目录，问题会索引自己，导致"自己命中自己"、命中率虚高。
→ 脚本现在会跳过评测题文件和 `--eval` 指定的文件。

**2. 变量混杂**
一次同时改切块和检索方式，分数变了却无法归因。
→ **一次只改一个变量**，这是评测存在的最大意义。

**3. 上下文过载**
k 从 3 提到 5，检索 top-3 命中率不变（9/9），但生成从 18/20 掉到 15/20。
有题目的证据明明在第 2 名，模型却说"资料里没有提到"。
→ 资料不是越多越好，噪音会稀释注意力。

**4. 指标选错**
只看 top-1 会得出"向量不如 BM25"的结论，从而扔掉一个最终效果更好的方案。
→ 指标要贴着下游任务选（我们下游用 top-3，就盯 top-3）。

**5. 裁判噪音**
LLM 当裁判时，"答对但漏了一个修饰词"会被扣分。评测集写得过细，会惩罚合理回答。
→ 参考答案只写核心信息，不要写细节。

**6. 混合检索不是银弹**
理论上 BM25 管专有名词、向量管语义改写，但在这份小语料上 RRF 融合反而更差
（把向量排第 2 的正确答案挤出了前 3）。**先测再用。**

## 已知限制

- **语料规模小**（实验时 15 块）：结论只在这个量级成立。语料放大到几千块后，排序噪声会下降，向量的优势会更明显
- **中文分词是 bigram**：`启动服务` → `启动` `动服` `服务`，够用但粗糙
- **无 rerank**：现在是"粗排取前 3"，标准做法是取前 10 再精排
- **单跳检索**：需要跨多段证据的问题（答案分散在两个段落里）会答不全
- **无权限控制**：所有文档对所有人可见
- **无流式输出**：接口等整段生成完才返回

---

## 下一步优先级

1. **rerank**：取 top-10 用 `bge-reranker-v2-m3`（硅基流动同样免费）精排出 top-3，性价比最高
2. **流式输出**：改善交互体验
3. **parent-document 检索**：小块检索、大块喂给模型，缓解"证据被切散"
4. **换真实语料**：这一步最重要——真实问题会和自编评测集长得完全不一样
